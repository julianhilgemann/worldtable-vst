# T3.3 — Progression: the sky writes the chords
**Milestone:** M3   **Depends on:** T3.2   **Branch:** feat/t3.3-progression

## Goal
The slow chord progression of `spec/05` §3 and `spec/01` §4: quiet → home, growth →
tension, onset → a chromatic mediant, recovery → a borrowed chord, with seeded choices,
no immediate repeats, wanders in long phases, and a "hold" at Progression 0. Port
`prototype/sky/sound/harmony.js`'s `Harmony` progression and `engine.js`'s per-tick
handshake to C++, drive it from the Sky Model's phase and onset events inside
`SkySound`, and prove it against the sound golden's chord requests and voicings.

## Design
- **`dsp::Harmony` grows the progression** (kept beside T3.2's chord hold):
  - `Phase { quiet, growth, onset, recovery }` (mirrors `sky::SkyPhase`; a
    `static_assert` in `SkySound.cpp` keeps the two in step).
  - `setProgression (0…1)`, `setSeed`; `start (Phase)` seeds the target from the
    phase without requesting (the host's start chord).
  - `onPhase (Phase, int modelMinute, const char* reason = nullptr)`: home always
    returns; other moves happen with probability = Progression, seeded by the model
    minute (`rand01 (seed, 61, minute)`), the chord index by `rand01 (63, minute)`, no
    repeat of the last index of that function (`last[4]`), and a newer request replaces
    a pending one. Weak onsets (< 0.3) take the tension move only
    (`spec/05` §12, T1.3 notes).
  - `onOnset (strength, modelMinute)`: ≥ 0.3 → the awe move, else the weak-onset tension.
  - `update (realS)`: a seeded wander inside the current function every
    `(150 + 210·rand01 (65, wanders)) / (0.5 + progression)` s, never while a request
    is pending (`rand01 (67, wanders)` picks the step). `take (realS)` clears the
    pending, restamps the clock and draws the next delay — the sketch's exact state.
  - `hasPending`, `pendingChord`, `pendingUrgent`, `pendingFunction`, `pendingIndex`,
    `pendingReason` (static `const char*`, no `std::string`), `take`.
  - The pending chord is built from the *current* key, Mood and Transpose when it is read;
    `SkySound` refreshes its copied request every tick while it waits, so a control moved
    while a chord waits is heard when it lands.
  - Threading: `update`/`take`/`pending*` are audio-thread; the setters stay atomic and
    set a `revoice` flag that `update` consumes (it re-requests the current target, or
    home at Progression 0), so the UI never writes the pending state. `start` and
    `setSeed` are called before playback.
  - Default Progression is **0** in C++ (the sketch's default is 1; the plug-in's
    parameter will be 1 in T3.6). That keeps T3.1's held-chord golden and tests untouched;
    the render tool opts in with `--progression 1`.
- **`SkySound` owns a `Harmony`** (`harmony()` accessor, like `PluginEngine`'s):
  - in `skyTicked`: phase events (all but `onset`) → `onPhase`; onset events →
    `onOnset`; then `harmony.update (realS)`. A pending request is copied into the
    existing bank queue once (the T3.1 bank logic is untouched), and when the chord is
    actually applied, `harmony.take (realS)` advances the wander clock.
  - `requestChord` (tests, later MIDI) stays the external path and marks the pending as
    not from Harmony.
  - `lastChordTick()` for tests/UI (the tick the chord was applied on).
  - Nothing changes when no Harmony pending exists: T3.1's sound and its golden replay
    bit for bit.
- **Render tool:** `--progression 0…1` (default 0); configure the Harmony, `start` it
  from the runtime's phase after `seek`, print the Progression and the applied changes.
- **Golden:** `tests/golden/sound/2024-05-10-1720.json` already carries the sketch's
  `requests` (ticks 4692, 10863) and the applied voicings/notes. The C++ progression
  must produce the same two chords on the same ticks with the same 3 × 64 notes, from
  the same start chord (Dmaj7sus2 = growth/tension[0]). No new golden is needed.

## Constraints
- Rule 1: no allocation, locks, I/O or logging in `onPhase`/`onOnset`/`update`/`take`/
  `pendingChord`; fixed arrays only.
- Rule 4: chords reach the sound through the double-banked queue; a new chord never
  retunes a ringing bank.
- Rule 5: same seed + same sky + same Progression + same sample rate → the same chord
  requests at the same ticks, whatever the block size. The RNG is
  `sky::rng::rand01`, the sky port's generator (bit-compatible with `rng.js`).

## Notes
- **Where it lives.** The progression state is in `dsp::Harmony` (`onPhase`, `onOnset`,
  `update`, `take`); `SkySound` owns one instance, feeds it each tick's `phase` events (all
  but `onset`) and `onset` events, calls `update`, copies a pending request into its bank
  queue, and calls `take` when the chord actually lands. The T3.1 `requestChord` path is
  unchanged for the tests (and later MIDI).
- **Defaults.** C++ Harmony starts at Progression 0 (hold); the sketch's 1 is the plug-in
  parameter default (T3.6). The render tool opts in with `--progression 1`. With 0, no
  progression code runs and T3.1's sound is bit-identical — the golden test still prints
  "null-test residual 135.2 dB below the signal".
- **The start phase.** `SkyRuntime::seek` only queues the request; the model's snapshot
  (and its `phase`) is updated on the next `process`. The render tool and the test call
  `runtime.process (0, nullptr)` after `seek` to apply it, then read
  `current().phase` for `Harmony::start`. This is the one surprising step for T3.4/T3.5
  and the plug-in: without it the start chord follows the pre-seek (quiet) phase.
- **The golden matches.** Progression 1, seed 1, 24×, 10 May from 17:20 UT: two changes,
  `B♭maj7` applied on tick 4692 and `Gm add9` on 10863, with the golden's 3 × 64 notes in
  the applied bank, from the golden's `Dmaj7sus2` start (the growth phase's tension[0]).
  The test also runs 128- and 37-sample blocks and a deterministic 64–2000 mix: the first
  change lands on the same tick in all four, and `process` allocates nothing through the
  two changes. The 60 s block-size runs are cheaper than replaying both changes four times
  (the golden run covers both).
- **Render** (`WorldtableRender --sky --from 17:20 --seconds 120 --progression 1`, Debug):
  `Dmaj7sus2 (I) start, progression 1.00; 2 changes -> Gm add9, 1 onset`; peak −1.0 dBFS,
  RMS −17.9 dBFS, max step 0.0448, no NaN/inf, 0 resets. A progression run starts exactly
  at `from` (no 20 s pre-roll, as the golden does); the held-chord run keeps its pre-roll.
  File: `renders/T3.3-2024-05-10-1720-24x-s1-progression.wav` (git-ignored).
- **Fixed in T3.6:** the 10 ms bed burst on a chord-change tick (T3.1 notes) — sketch and
  port together, golden re-exported on purpose. **Decided in T3.6:** MIDI vs progression —
  while notes are latched the held chord is authoritative, the sky keeps sensing, and the
  last note-off hands the sky's current chord back (spec/05 §3).
- **Checks:** ctest 76/76 (the new golden case is ~78 s, total ~3.5 min Debug); AU, VST3
  and Standalone build with no new warnings; `pluginval --strictness-level 8` SUCCESS; the
  sketch's 15/15 tests are unchanged. T3.1's sound golden is untouched.
